# WPForms "tick every box" — conservative plan (2026-09-15)

Third occurrence of the same problem, this time on the **seminar registration form 15199**
(<https://fbhi.se/sv/online-seminarium-30-september-2026/>). Earlier rounds: [README.md](README.md)
(June, IWG form 14741) and [2026-08-recurrence.md](2026-08-recurrence.md) (August, same form).

This document supersedes the August fix list as the working plan. The August list was written to make
the form survive without JavaScript at any cost. The plan below is deliberately more conservative:
change only what is plainly wrong, keep the spam protection and the required fields, monitor, and keep a
fool-proof fallback ready if the problem persists.

## 1. What we know (verified read-only on prod, 2026-09-15)

- **Symptom:** the browser demands that every box in a checkbox group is ticked before the form can be
  sent. Some visitors also get "Attempt to submit corrupted post data" after ticking everything.
- **Mechanism:** WPForms puts a native `required` attribute on every checkbox of a required group. The
  browser validates each box separately, so it wants them all. WPForms' JavaScript normally hides this
  by disabling native validation and using its own group rule ("one tick is enough"). When that
  JavaScript does not run, the native behaviour shows through.
- **"Corrupted post data" corrected (2026-09-15, from the WPForms 2.0.1.1 source):** this error is raised
  in `WPForms_Process::process()` when a form has **"Enable AJAX form submission"** on and receives a
  plain non-AJAX POST — which is what a visitor without working JavaScript sends. It is **not** the
  anti-spam token check (that one says "Antispam token is invalid"). The June/August notes blamed the
  token; the first barrier for a JS-dead submit is the AJAX setting. The token check comes later and
  its failures are logged even with logging off (`force`) — the log table shows **zero** token
  rejections since 2025-02 (IDs 1–111 contiguous, no deletions). Token validity covers five years of
  past days plus 45 minutes, so a stale cached page cannot cause a token failure either.
- **It is intermittent and self-healing.** Reloading the page fixes it. Every time we have inspected the
  site, the JavaScript was healthy: no console errors, all scripts loaded, validation attached. Form
  15199 received 135 entries in its first week, so the great majority of visitors are unaffected.
- **Working hypothesis for the JavaScript failure: hosting under load.** A single script request that
  times out or returns an error under load is enough to leave the form in its native state for that page
  load. This has not been proven; the monitoring in section 4 is designed to catch it.
- **What is plainly wrong in the forms:** single-answer questions are built as **checkbox groups with
  "choice limit 1"**. That emulates a radio button in JavaScript. A **Multiple Choice (radio)** field is
  the correct control for a single answer: the browser enforces "pick exactly one" natively, with or
  without JavaScript. This mistake is the only reason the reported symptom looks the way it does.
- **What is standard WPForms and worth keeping:** required multi-select checkbox groups, the modern
  anti-spam token, and required fields hidden by conditional logic. All three depend on JavaScript by
  WPForms' design. Every WPForms site uses them.
- **Licence:** WPForms Pro plugin 2.0.1.1 on a **Basic** licence (active, auto-renewing, expires
  2026-09-16 and should renew automatically). "Upgrade to Pro" buttons in wp-admin are the tier notice,
  not a problem. Radios, honeypot, keyword and country filters are all available on Basic.

## 2. Phase 1 — do now (form builder, wp-admin)

These are the only changes in this phase. Nothing about spam protection or required fields changes.

1. **Form 15199** — replace fields **42, 41, 51** with Multiple Choice (radio) fields, required, same
   label, description and choices, same position. Field 42 carries an empty leftover conditional-logic
   rule; leave it off on the new field. Keep field 64 (role) as a required checkbox group.
2. **Form 14741** — replace fields **100, 101** with Multiple Choice (radio) fields, required. Field
   **126** ("If Other, please describe") is shown by conditional logic when field 101 = "Other (please
   specify below)"; re-point that rule at the new radio field's "Other" choice. Leave everything else.
3. **Form 13921** — replace field **90** with a Multiple Choice (radio) field, required.
4. **Future seminar forms** — duplicate from the corrected 15199 from now on.
5. **Enable WPForms logging** (WPForms → Tools → Logs; types Spam, Errors, Security). This is the
   only way to count "corrupted post data" rejections. Done 2026-09-15 (see change log).
6. **Purge the Nginx cache** for each affected page (Nginx Helper) after saving. The form markup is
   part of the cached page; saving a form does not purge the page cache on its own.
7. **Verify without submitting:** reload each page and confirm the questions render as radios, one
   choice can be selected, and the console is clean. No test submission is needed for this phase. If a
   test submission is wanted, enable email test mode first (notifications go to
   annika.norell.benson@fbhi.se).

How the type change is made: WPForms' builder cannot change a field's type in place (the manual
route is add a Multiple Choice field, copy everything over, delete the checkbox field, which gives the
question a new field ID and splits old and new entries into two columns). To keep the field IDs, the
existing entries and any conditional rules pointing at these fields, the change is instead made directly
in the stored form data through WPForms' own save routine (`wpforms()->obj('form')->update()`), via the
Novamira prod MCP with Daniel's explicit per-form authorisation. Verified against the WPForms 2.0.1.1
source: the Multiple Choice field uses every setting a Checkboxes field stores except `choice_limit`;
the change sets `type` to `radio` and removes `choice_limit` (and, on 15199 field 42, the empty
leftover conditional-logic keys). Nothing else in the field or form is touched, and WPForms saves a
revision as it does for a builder save. Backups: full site backup by Daniel plus WPForms export files in
`backups/` (re-importable via WPForms → Tools → Import). The export files must be saved as the raw response text:
parsing the JSON in JavaScript first reorders integer-like keys and silently loses the field and choice order.

## 3. What Phase 1 achieves, and what it does not

- The reported symptom ("tick every box") **cannot occur** on the changed questions any more, with or
  without JavaScript. Radios have no "all boxes" state.
- A visitor whose JavaScript fails can still be blocked on a **required multi-select** (field 64 on
  15199, fields 103 and 125 on 14741) and would still be rejected by the **anti-spam token** on submit.
  That residual case is what the monitoring phase measures. It is accepted deliberately, to keep spam
  protection and data quality until we know how often it really happens.

## 4. Phase 2 — monitor (suggested 4–6 weeks, at least through the 30 Sep seminar and the next one)

1. **WPForms logs**, weekly: count "corrupted post data" / token rejections and errors, with times.
2. **Reports from users**: for every report, record date, time, browser, device, and whether a reload
   fixed it. A report that mentions "corrupted post data" or "had to tick all roles" is the residual case
   from section 3.
3. **Hosting logs**: for the timestamps above, ask Loopia for access/error log lines showing any
   `.js` request that returned an error or timed out. This confirms or rules out the hosting hypothesis.
4. **Optional probe (child theme, deployed via git):** a small script on pages that contain a WPForms
   form. A few seconds after page load it checks whether WPForms took over the form (`novalidate` set,
   validator attached). If not, or if a script error occurred, it sends one beacon with the browser,
   the failing script URL and the error text to a small log kept in WordPress. This is the only way to
   catch the failure in the act. Built and tested on dev first.

### Observation 2026-09-24 — failure caught in a real browser (Chrome MCP, before the plugin updates)

On a **cold first load** of the seminar page (15199, WPForms 2.0.2) Chrome logged
`Uncaught ReferenceError: wpforms_settings is not defined` from `wpforms.min.js` `loadValidation`, and the
form stayed **un-initialised** (`novalidate=false`, no validator) — exactly the JS-dead state that turns a
submit into "corrupted post data". A reload initialised normally. The same cold-load race hit `/calendar/`
(TEC views: `Cannot read properties of undefined (reading 'selectors')` ×10); reload clean.

Mechanism (from the page source): every script is `defer`, **including jQuery**, and Autoptimize turns inline
scripts into deferred `data:` URIs placed *after* their handles — `var wpforms_settings` is script #46,
`wpforms.min.js` #37. A deferred jQuery sees `readyState = "interactive"` and fires `.ready()` handlers on a
`setTimeout` instead of waiting for `DOMContentLoaded`; when a later deferred script is still downloading
(cold cache, slow host), that timer runs between script executions and WPForms' ready handler reads
settings that do not exist yet. Warm cache → scripts run back-to-back → no failure, which fits the
"intermittent, reload fixes it" reports.

Not yet acted on. Candidate fixes (dev first): exclude jQuery (and/or the WPForms/TEC handles) from
Autoptimize's defer, or keep inline scripts inline ("Also aggregate inline JS" / "defer inline" off) so
`wpforms_settings` exists before `wpforms.min.js` runs. This would remove the root cause rather than the
Phase 3 fallbacks.

**Decision rule at the end of the period:** if the logs and probe show zero or near-zero failures, the
issue is closed with Phase 1 only. If failures continue, proceed to Phase 3.

## 5. Phase 3 — fool-proof fallback (only if monitoring shows continued failures)

Makes every form work with no JavaScript at all. Each step costs something, listed honestly.

1. **Server-side `novalidate` (child theme, one filter on `wpforms_frontend_form_atts`).** Turns off
   the browser's native validation for all WPForms forms up front, which WPForms' JavaScript does anyway
   when it runs. A visitor without JavaScript then submits normally and gets WPForms' server-side
   validation messages instead of the browser wall. Required multi-selects and hidden conditional fields
   **stay required**, enforced on the server. Cost: none in normal operation; must be tested on dev.
2. **"Enable AJAX form submission" off** for the affected forms (Settings → General). Without it a
   non-AJAX POST is rejected as "corrupted post data" before anything else runs. Cost: the page reloads
   on submit instead of updating in place; confirmations still work. **Then** anti-spam: modern token
   off, honeypot on, because a submission without the JavaScript-injected token is rejected next. Cost:
   weaker bot protection. Compensate with the **keyword filter**, the **country filter** (allow Sweden on the
   Swedish seminar forms), **Akismet**, and "store spam entries" so rejected submissions can be reviewed.
   Do not substitute a captcha; it re-adds the JavaScript dependency.
3. **Only if step 1 is not wanted:** make the required multi-select groups optional (15199 field 64;
   14741 fields 103, 125) and the hidden conditional textareas optional (14741 fields 98, 120, 126).
   Cost: loss of the "must answer" guarantee. Step 1 is preferable because it keeps them required.
4. **Hosting:** if Phase 2 shows scripts failing under load, that is a hosting capacity conversation
   (plan upgrade or move), independent of the form changes.
