# FBHI Guides – WordPress Implementation Brief

*Daniel's original brief, received 2026-09-02, verbatim.*

## Project goal

Build a custom guide/handbook system for the existing FBHI WordPress website.

The functional and visual reference is Jämställdhetsmyndigheten’s digital handbook:

https://jamstalldhetsmyndigheten.se/mans-vald-mot-kvinnor/att-forebygga-mans-vald-mot-kvinnor/inget-att-vanta-pa-som-digital-handbok/

The implementation should follow WordPress core conventions as closely as practical, use Gutenberg for editing, integrate naturally with the existing Salient theme and child theme, and remain maintainable through future WordPress updates.

The initial implementation is for Swedish content only, but it must be prepared for WPML, which is already used on the site.

## Existing environment

* WordPress
* Salient theme
* Existing Salient child theme containing other custom site-specific functionality
* WPML
* Existing custom post type integrations in the child theme already reuse Salient templates and theme functionality where appropriate

The guide functionality can be implemented as a self-contained module within the existing child theme rather than as a separate plugin.

Guide-related code should nevertheless be kept isolated in its own classes/files so that it could be moved into a plugin later if required.

Salient-specific rendering should preferably remain separated from the core guide/data logic.

## Content model

Create a hierarchical custom post type, tentatively named `guide`.

A top-level Guide post represents the guide itself and acts as its index/start page.

Child posts represent chapters or steps.

Example:

```text
FINGER Implementation Guide
├── Introduction
├── Step 1
├── Step 2
├── Step 3
├── Step 4
└── Step 5
```

The WordPress parent/child hierarchy and `menu_order` should be used where practical rather than introducing a separate relationship system.

The architecture should also allow deeper child levels if needed later.

## Gutenberg editing

Guide content should use the standard WordPress block editor.

Prefer WordPress core blocks wherever possible.

For the `guide` post type, curate the editor experience by limiting the available blocks to those relevant for this type of content. The purpose is to make editing easier for less experienced editors and avoid unnecessary Salient/plugin blocks.

Potential core blocks include:

* Paragraph
* Heading
* List
* Image
* Gallery
* Buttons
* Quote
* Group
* Columns
* Table
* File

Guide-specific presentation elements should preferably use, in order of preference:

1. Core blocks
2. Custom block styles
3. Block patterns
4. Custom Gutenberg blocks where actual custom behaviour/data is required

Examples of guide-specific components could include information boxes, callouts and similar elements.

## Guide index page

The root Guide post acts as the guide index page.

Its normal Gutenberg content can be used for the introduction.

The chapters/steps belonging to the guide should then be presented automatically as an index, visually similar in principle to the reference site.

Each chapter/step should have:

* Title
* Optional short description/excerpt
* Sort order
* Configurable accent colour

The index cards should be generated from the guide hierarchy rather than manually duplicated by the editor.

A dedicated Guide Index Gutenberg block may be appropriate if it gives useful control over where/how the automatically generated index is inserted.

## Chapter colours

Each main chapter/step should support a configurable accent colour.

The same colour should automatically be reused consistently for that chapter, for example:

* Chapter card on the guide index
* Chapter/page header
* Relevant navigation accents
* Other guide-specific visual elements where appropriate

If chapters later contain nested child pages, they should be able to inherit the colour from their main chapter.

The editor should set the colour once rather than manually styling individual blocks.

## Guide page template

Guide pages should have a dedicated Salient-compatible frontend template in the child theme.

The template should follow the existing FBHI/Salient design system rather than creating a visually isolated application.

Reuse existing theme typography, spacing, responsive behaviour, header/footer conventions and other suitable Salient styling/components.

Guide-specific design should complement the existing site.

The chapter header should be generated by the template rather than manually built inside Gutenberg.

It may contain information such as:

* Chapter/step designation
* Page title
* Optional introduction
* Chapter accent colour

## Automatic table of contents

Chapter pages should automatically generate an on-page table of contents from headings within the Gutenberg content.

Initial behaviour:

* Primarily use H2 headings
* Automatically create/use heading anchors
* No manual duplication of navigation items by editors

Desktop:

* Display the content navigation in a right-hand column
* Preferably sticky while reading, where suitable

Mobile:

* Display the same navigation as a compact expandable/dropdown control

The generated navigation and page content must remain synchronized automatically when headings are changed.

Support for additional heading levels can be added if required, but avoid unnecessary complexity initially.

## Guide navigation

The hierarchy should be available for automatic navigation between guide sections.

Where appropriate, support:

* Current chapter indication
* Previous chapter
* Next chapter
* Link back to the guide overview

Navigation should be generated from the WordPress hierarchy/order rather than entered manually.

## Guide settings / metadata

Keep custom metadata minimal.

Potential guide/chapter metadata includes:

* Accent colour
* Optional guide-specific display settings
* Optional short index description if the native excerpt is not suitable

Prefer native WordPress metadata APIs where the requirements are simple.

ACF should only be introduced if the final requirements make the metadata substantially more complex or if using the existing ACF setup on the site provides a clear advantage.

## Last updated date

At the bottom of each guide/chapter page, automatically display:

**Last updated:** [date]

For Swedish:

**Senast uppdaterad:** [datum]

Use WordPress' actual post modified date rather than requiring editors to enter this manually.

The date should follow the site's locale and WPML language.

## Print styling

Provide dedicated print CSS for guide pages.

The printed version should:

* Remove unnecessary site/navigation UI
* Preserve a clear content hierarchy
* Use sensible print typography and widths
* Handle page breaks reasonably
* Avoid awkward breaks around headings, boxes and similar components where possible

This is browser print optimisation, not a PDF generation system.

## Responsive behaviour

The full guide experience must work on desktop and mobile.

Particular attention should be given to:

* Guide index cards
* Chapter headers
* Content width
* Right-side table of contents on desktop
* Dropdown/expandable table of contents on mobile
* Guide navigation
* Images and custom content components

## WPML / internationalisation

The first release only needs Swedish content, but the implementation must be WPML-ready.

Requirements include:

* Register the Guide post type in a WPML-compatible way
* Ensure guide hierarchy can be translated correctly
* Define appropriate translation/copy behaviour for guide metadata such as accent colours
* Do not hard-code user-facing strings
* Use WordPress internationalisation functions and a consistent text domain
* Ensure generated labels such as “Contents”, “Previous”, “Next” and “Last updated” can be translated
* Ensure date output follows the active locale

Avoid implementation choices that would make adding translated guides difficult later.

## Code organisation

Keep guide functionality isolated inside the Salient child theme, for example:

```text
salient-child/
├── includes/
│   └── guides/
│       ├── class-guides.php
│       ├── class-guide-editor.php
│       ├── class-guide-navigation.php
│       ├── class-guide-meta.php
│       └── ...
├── single-guide.php
└── assets/
    ├── css/
    │   ├── guides.css
    │   └── guides-print.css
    └── js/
        └── guides.js
```

The exact file structure can be adjusted to fit the existing child theme conventions.

Avoid putting substantial guide logic directly into `functions.php`.

Keep general WordPress guide logic reasonably independent from Salient-specific rendering so that the functionality could be extracted into a plugin in the future without a major rewrite.

## General implementation principles

* Stay close to WordPress core APIs and Gutenberg.
* Avoid unnecessary dependencies.
* Avoid building a separate CMS-like editing interface.
* Automate information that WordPress already knows.
* Avoid requiring editors to maintain the same information in multiple places.
* Keep the editor experience simple and constrained.
* Follow the existing FBHI/Salient design wherever possible.
* Build only the custom components that the guide format actually requires.
* Keep the implementation customer-specific and pragmatic rather than attempting to create a generic public guide framework.
